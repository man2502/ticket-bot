# Веб-панель

Управление поиском и бронированием билетов: пассажиры, процессы, брони,
настройки сервисов, разметка капч.

Панель **не содержит логики поиска**. Она хранит настройки, запускает ботов
(`railway-api/railway_check.py`, `airlines_api/api_check.py`) отдельными
процессами и показывает их вывод. Боты остаются работоспособными и из CLI.

## Установка

```bash
.venv/bin/python -m pip install -r requirements-web.txt
.venv/bin/python -m web.cli create-admin
```

Windows:

```cmd
.venv\Scripts\python.exe -m pip install -r requirements-web.txt
.venv\Scripts\python.exe -m web.cli create-admin
```

Учётной записи по умолчанию нет: панель ведёт к странице оплаты, и забытый
`admin/admin` здесь стоит слишком дорого.

## Запуск

```bash
./run_web.sh          # macOS / Linux
run_web.cmd           # Windows
```

По умолчанию `http://127.0.0.1:8000`. Адрес меняется переменными
`TICKET_HOST` и `TICKET_PORT`.

## Данные

Всё рабочее лежит в `web/data/` (в git не попадает):

| Файл | Что |
|------|-----|
| `ticket.db` | SQLite: пользователи, пассажиры, процессы, логи, брони |
| `secret.key` | ключ шифрования паролей в базе |
| `session.key` | ключ подписи cookie |
| `captcha/` | картинки нерешённых капч |
| `runs/` | временные `check.env` и `passengers.json` запусков |

**Про ключи.** Пароли T5/Railway, SMTP и ключ SMS хранятся в базе
зашифрованными, ключ лежит отдельным файлом. Копия `ticket.db` без `secret.key`
паролей не выдаёт. Потеря `secret.key` — пароли придётся ввести заново
(остальные данные целы).

На сервере ключи удобнее задавать переменными `TICKET_SECRET_KEY` и
`TICKET_SESSION_KEY` вместо файлов.

## Устройство

```
web/
  app.py         сборка приложения: роутеры, статика, страницы ошибок
  auth.py        вход, require_user / require_admin
  cli.py         команды обслуживания
  config.py      пути, порт, каталоги
  crypto.py      Fernet для секретов
  db.py          подключение к SQLite
  models.py      схема базы
  security.py    scrypt-пароли, cookie сессии
  templating.py  общий контекст шаблонов и меню
  routes/        по разделу на файл
  services/      логика без HTTP: валидация, справочники, уведомления
  templates/ static/
```

Роуты и логика разделены намеренно: `services/` не знает ни про FastAPI, ни про
ORM, поэтому валидацию можно прогнать тестами без поднятия приложения.

## Разделы

| Раздел | Кому | Что делает |
|--------|------|------------|
| Процессы | всем | создание поиска, запуск, остановка, живая консоль |
| Пассажиры | всем | общий справочник для самолётов и поездов |
| Брони | всем | ссылки на оплату, история, снятие блокировки (админ) |
| Справочники | админу | станции и аэропорты, пересинхронизация |
| Капчи | админу | разметка того, что не решила модель |
| Настройки | админу | почта, SMS, доступы и лимиты сервисов |
| Пользователи | админу | создание, блокировка, смена пароля |

Панель управляет только `airlines_api` и `railway-api`. Модули в `other/`
(браузерный бот и Çapar) работают из командной строки и сюда не входят.

## Пассажиры

Список общий для самолётов и поездов: один человек и летит, и едет, а вести его
данные в двух местах — верный способ получить два написания фамилии в паспорте.

Проверки при вводе (`web/services/passengers.py`):

* имя и фамилия — только латиница, приводятся к верхнему регистру, как в паспорте;
* дата рождения — любой из привычных форматов, приводится к `ДД.ММ.ГГГГ`;
* номер документа — без пробелов и дефисов, уникален по всей базе;
* телефон — `61234567`, `861234567`, `+993 61 23 45 67` дают один результат;
* срок действия документа — предупреждаем, если уже истёк.

**Тип пассажира** по умолчанию не задаётся вручную, а считается от даты рейса:
младенец до 5 лет, ребёнок до 18. Считать «на сегодня» нельзя — ребёнок,
которому 18 исполняется до вылета, летит по взрослому тарифу.

Состав группы проверяется при создании процесса: ребёнок не поедет без
взрослого, а младенцев не может быть больше, чем взрослых.

Удалять пассажиров может только админ, и только если они не участвуют
в незавершённых процессах.

## Справочники

Станции поездов и аэропорты хранятся локально, в одной таблице, разделённые
полем сервиса. Так форма создания процесса открывается сразу и работает, когда
сайт перевозчика лежит — а лежит он обычно ровно тогда, когда билеты и ищут.

| Сервис | Источник | Записей |
|--------|----------|---------|
| Самолёты | `turkmenistanairlines.tm/ru/get_internal_ports` | 7 |
| Поезда | `api.railway.gov.tm/v2/stations` | 142 |

Аэропортов нет в iOS-API, поэтому берём их с сайта. В браузерном боте этот же
адрес дёргается через `page.evaluate`, но обычного HTTPS-запроса достаточно —
авторизация не нужна, браузер тоже.

При первом запуске панель наполняет пустые справочники сама. Дальше — кнопка
«Обновить» в разделе, доступном только админу.

**Пропавшие станции не удаляются, а помечаются как неактивные.** На станцию
могут ссылаться уже созданные процессы, и удаление оставило бы в базе процесс
с маршрутом «ниоткуда никуда». Вернулась в источник — снова станет активной.

**Недоступный источник не очищает справочник.** Пустой список хуже устаревшего:
с ним нельзя даже создать процесс. Ошибка показывается, старые записи остаются.
Пустой ответ от источника тоже считается сбоем, а не «станций больше нет».

## Настройки

### Секреты

Пароли SMTP, ключ SMS и пароли перевозчиков лежат в базе зашифрованными
и **никогда не отдаются в HTML** — форма показывает только признак «задан».

Правила работы с полем секрета одинаковы везде:

| Что ввели | Что произойдёт |
|-----------|----------------|
| пусто | значение не меняется |
| новое значение | заменяется |
| `-` | стирается |

«Пусто = не менять» существенно: иначе правка соседней галочки молча обнуляла
бы пароль, и выяснилось бы это в момент брони.

### Проверка связи

У почты и SMS есть кнопка «Отправить тест». Неверный пароль должен обнаружиться
сейчас, а не тогда, когда бронь создана, а ссылка на оплату не дошла. Для Gmail
нужен **пароль приложения** — обычный пароль сервер отклоняет с кодом 535,
и панель прямо это подсказывает.

### SMS-шлюз

Панель шлёт `POST` с телом JSON. Имена полей и способ передачи ключа
настраиваются: у разных провайдеров они разные.

* поле номера, поле текста, имя параметра ключа — задаются;
* ключ уходит в тело, в заголовок или в query — на выбор;
* ключ необязателен;
* адрес обязан быть `https` — ключ не должен уходить открытым текстом;
* повторов при сбое нет: шлюз мог принять запрос, и повтор дал бы второе SMS.

### Параметры сервисов

Свободного поля «проверять каждые N секунд» нет намеренно: боты стреляют
в фиксированные секунды минуты с небольшим разбросом, и произвольный интервал —
прямой путь к бану. Настраивается то, что настраивать безопасно: какие окна
включены, секунда первого окна, лимит поисков в час, паузы backoff.

Числовые поля ограничены с обеих сторон. Например, паузу после `HTTP 429`
нельзя опустить ниже 30 секунд — это гарантия бана вместо билета.

У поездов раздела доступов нет: API открытый. У самолётов нужны телефон
и пароль личного кабинета плюс пароль приложения — по ним бот сам получает
Bearer-токены и обновляет их, когда те протухают.

## Процессы

### Как запускается бот

```
панель → пишет check.env и passengers.json в web/data/runs/job-N/
       → запускает railway_check.py --env .../check.env отдельным процессом
       → построчно читает stdout в потоке → job_logs → SSE в браузер
       → по коду выхода ставит статус
```

Боты **не переписывались** под панель: они по-прежнему читают настройки из файла
окружения. Отлаженная логика антибота — тайминги слотов, ротация User-Agent,
backoff, защита от повторной брони — не тронута.

Файл, а не переменные окружения, потому что внутри бота стоит
`load_dotenv(path, override=True)` — он перезаписал бы всё, что передано через
`os.environ`.

Почта у бота намеренно не настраивается: `GMAIL_*` не передаём, рассылает панель.

### Коды выхода

| Код | Статус | Что значит |
|-----|--------|------------|
| 0 | `booked` | места найдены или бронь создана |
| 2 | `needs_review` | **бронь под вопросом** — подтверждение ушло, ответа нет |
| 1 | `failed` | ошибка |
| 0 после команды «Остановить» | `stopped` | бот корректно закрылся |

Код 2 — самый важный: повторный запуск может создать вторую настоящую бронь
и второй счёт. Панель показывает предупреждение и ждёт, пока человек проверит
брони у перевозчика.

### Один процесс на сервис

Два параллельных поиска с одного адреса в одну секунду — это бан, а не вдвое
больше шансов. Второй запуск по тому же сервису отклоняется с объяснением.
Поезд и самолёт друг другу не мешают — это разные сайты.

### Остановка

Панель шлёт `CTRL_BREAK_EVENT` (Windows) или `SIGINT` группе процессов (Linux),
бот ловит `KeyboardInterrupt`, дописывает журнал броней и выходит. Если за 15
секунд не вышел — убивается принудительно.

Чтобы это работало на Windows, понадобились две правки в общем коде:

* `core.bootstrap` ставит обработчик `SIGBREAK` — Python, в отличие от `SIGINT`,
  сам его в `KeyboardInterrupt` не превращает, и процесс умирал на месте, не
  дописав журнал броней;
* `core.slots.precise_sleep` спит кусками по 0.5 с — `time.sleep` на Windows
  не прерывается сигналом, и в ожидании слота бот не реагировал на команду
  до минуты. Точность слота при этом не изменилась.

### После перезапуска панели

Процессы не переживают её остановку, а записи «в работе» в базе остаются.
При старте панель помечает их остановленными — иначе очередь сервиса
оказалась бы занята навсегда.

## Брони

### Источник правды — журнал бота

Ссылка на оплату и номер брони берутся из `railway-api/railway_bookings.json`
и `airlines_api/api_bookings.json`, а не из печати в консоль: там они лежат
структурно, рядом со статусом попытки.

Этот же журнал защищает от повторной брони и переживает падение процесса.
Панель его **только читает**; дублировать его логику было бы ошибкой — две
«правды» рано или поздно разойдутся, и разойдутся на деньгах.

Журнал общий для всех запусков сервиса, поэтому записи отбираются по времени:
всё, что начато не раньше старта процесса. Иначе бронь прошлого запуска
приписалась бы текущему, и человек получил бы письмо о старой броне.

### Блокировка

| Статус попытки | Блокирует запуск | Что значит |
|----------------|:----------------:|------------|
| `done` | да | бронь создана |
| `unknown` | да | ответ потерян — бронь **могла** быть создана |
| `pending` | да | процесс не дожил до ответа |
| `failed` | нет | сервер достоверно отказал, брони нет |

Пока блокировка есть, панель отказывает в запуске **заранее**, с объяснением.
Без этого бот запускался бы и молча завершался через секунду.

### Снятие блокировки

Только админ и только с подтверждением: в поле нужно вписать слово «снять».
Это ровно то, что делает флаг `--force-rebook` у ботов.

Опасность в том, что блокировка обычно означает «бронь могла быть создана».
Снять её, не проверив брони у перевозчика, — значит рискнуть вторым счётом
на тех же пассажиров. Поэтому в карточке блокировки прямо написано, что
проверить, и одной кнопки недостаточно.

Записи в панели после снятия помечаются, но не удаляются — история нужна.

### Рассылка

После завершения процесса панель подбирает новые брони из журнала и по тем,
где есть ссылка на оплату, отправляет письмо и SMS. Получатель — из процесса,
а если там пусто, из общих настроек. Каждая отправка попадает в журнал: видно,
ушло письмо или нет. Если не ушло — есть кнопка «Отправить снова».

Про «бронь под вопросом» письмо со ссылкой не шлётся: ссылки нет, а тревогу
человек уже видит в карточке процесса и в разделе броней.

## Капчи

Капча есть только у самолётов — у поездов её нет вовсе.

Процесс поиска **никогда не ждёт человека**: не решилась капча — берётся новая,
а картинка складывается в датасет. Админ разбирает накопленное в свободное
время, размеченное идёт в обучающую выборку.

### Откуда берутся картинки

| Папка | Что там |
|-------|---------|
| `rejected/` | модель дала код, сервер его отверг — есть ошибочный вариант |
| `unlabeled/` | код неизвестен вообще |
| `hard/` | размеченное вручную, идёт в обучение с повышенным весом |
| `confirmed/` | капчи, которые сервер принял |

Всё это лежит в `airlines_api/captcha_dataset_api/`. **Источник правды — файлы,
а не база**: боты пишут туда напрямую, ничего не зная про панель, и вторая
копия в базе означала бы расхождения. База ведёт только журнал разметки.

Ошибки модели показываются первыми: на них она и учится.

### После разметки

Модель нужно дообучить руками:

```bash
python airlines_api/train_captcha_cnn_api.py --resume
```

### Безопасность

Имя файла приходит из адреса страницы, поэтому проверяется, что оно не уводит
за пределы датасета: `../../secret.key` в имени — классический способ прочитать
чужой файл через веб. Картинки отдаются с `Cache-Control: no-store` — после
разметки файла уже нет, и закешированная превратилась бы в «призрак».
